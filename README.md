# Bulk Certificate Generator

Submit one batch of recipients and get one PDF certificate per recipient,
generated by a background worker. Design decisions: [docs/design.md](docs/design.md).

> Status: Phase 5. `POST /api/v1/jobs` validates and stores a job and
> publishes it to Redis; the Celery worker generates the certificates. Status
> and download endpoints come in Phase 6 (until then, inspect the database);
> the full README in Phase 8.

Sample certificates: [examples/sample-certificates/](examples/sample-certificates/)
(ordinary name, maximum-length text, accented and non-Latin characters).

## Quick start

Requires Docker with Compose v2.

```bash
docker compose up --build
```

This starts PostgreSQL, Redis, a one-off migration container
(`alembic upgrade head`), the API, and the Celery worker. Then open:

- Health check: http://localhost:8000/health
- Swagger UI: http://localhost:8000/docs

## Try the full flow

1. Submit the sample batch (two valid recipients, one invalid). The API stores
   the job, publishes its ID to Redis, and returns `202`; it does not generate PDFs:

```bash
curl -X POST http://localhost:8000/api/v1/jobs -H "Content-Type: application/json" --data @examples/job-request.json
```

2. The worker picks it up within moments. Its log shows the job finishing:

```bash
docker compose logs worker
```

3. Inspect the stored outcomes:

```bash
docker compose exec db psql -U certificates -d certificates -c "SELECT input_index, status, name, storage_key, error_details FROM job_recipients ORDER BY created_at, input_index;"
```

4. Copy a generated PDF out of the shared certificate volume (`STORAGE_KEY` is
   the `storage_key` value, `<recipient id>.pdf`):

```bash
docker compose cp worker:/data/certificates/STORAGE_KEY ./certificate.pdf
```

If Redis is unavailable, the submission returns `503 dispatch_failed` and the
job is recorded as `FAILED`; submit it again later. To run a queued job by
hand, without Celery:

```bash
docker compose exec worker python -m app.cli process-job JOB_ID
```

It prints the outcome as JSON (exit code 0; 1 for an unknown job; 2 if a
database error stopped processing). Finished or already running jobs are
reported as `already_finished` / `already_processing` and left untouched.
Behaviour when a worker is stopped or crashes is described in
[docs/design.md](docs/design.md#worker-interruption-observed-behaviour).
Set `WORKER_CONCURRENCY` (default 2) to run more jobs in parallel.

Names, event names, and issuer names may only use the supported scripts
(Latin, Greek, Cyrillic; see [docs/design.md](docs/design.md#certificate-text-policy-supported-characters)).
Other text is rejected at submission with `unsupported_characters`.

## Tests

```bash
docker compose run --rm --build tests
```

Tests use a separate database, `certificates_test`, which they drop,
recreate, and migrate on every run. They refuse to start if
`TEST_DATABASE_URL` could be the application database. Expect one known
warning (`StarletteDeprecationWarning` about `httpx`); see
[docs/design.md](docs/design.md#testing).

Regenerate the sample certificates:

```bash
docker compose run --rm --build --no-deps -v "$PWD/examples/sample-certificates:/out" tests python -m scripts.render_sample_certificates /out
```

## Dependencies

`requirements.in` and `requirements-dev.in` list direct dependencies.
`requirements.txt` and `requirements-dev.txt` are generated lock files; do not
edit them by hand. To re-lock after changing an `.in` file:

```bash
docker run --rm -v "$PWD":/src -w /src python:3.12-slim sh -c "pip install -q uv && uv pip compile requirements.in --universal --python-version 3.12 -o requirements.txt && uv pip compile requirements-dev.in --universal --python-version 3.12 -o requirements-dev.txt"
```
